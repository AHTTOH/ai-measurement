## 결정

수험생 서버를 여러 대 띄워 로드밸런서(라운드로빈 가능, 세션 고정 불필요) 뒤에 둘 수 있게 한다. 서버 메모리에만 있던 공유 상태를 PostgreSQL로 옮긴다.

| 상태 | 이전 | 이후 |
|---|---|---|
| 시험 상태(열기·종료) | 서버 캐시 | 매 조회 DB에서 읽음(권한 분리 때 이미 반영) |
| 대화별 응답 진행 중 여부(동시 전송 방지) | 서버 메모리 | `ai_streams` 행. 예약은 INSERT 한 번으로 원자적이다 |
| 진행 중 응답 조각(다른 서버에 붙은 응시자에게 전달) | 서버 메모리 구독자에게만 | 같은 서버 구독자는 메모리로, 다른 서버 구독자는 LISTEN/NOTIFY로 |
| 진행 중 응답의 지금까지 텍스트(새로고침·재접속) | 서버 메모리 | 다른 서버가 요청하면 응답을 맡은 서버가 `ai_streams.snapshot`에 써 주고 알린다 |
| 끝난 응답(done·failed 이벤트) | 메모리 구독자에게만 | `ai_streams.terminal`에 저장하고 알린다. 알림은 작게, 내용은 행에서 읽는다 |
| 응시자별 AI 요청 한도(분당) | 서버 메모리 | `rate_limit_hits` 행(슬라이딩 윈도). 확인·기록은 DB 함수 `rate_limit_try_acquire` 한 번 |
| 응시번호별 로그인 실패·잠금 | 서버 메모리 | `rate_limit_hits` 행. 여러 서버로 나눠 시도해도 잠긴다 |
| IP별 로그인 시도 한도 | 서버 메모리 | 그대로 서버별 메모리. 로그인 해시 계산으로부터 그 서버의 CPU를 지키는 한도라 서버마다 따로 세는 것이 맞다. DB에 두었더니 시험장 전체가 한 IP일 때 버킷 하나에 잠금 대기가 쌓였다(부하 결과 문서) |
| 만료 세션 정리 | 한 서버 | 모든 서버가 돌아도 같다(행 잠금 후 상태 확인, 이미 끝났으면 건너뜀) |

관리자 서버의 로그인 한도는 메모리에 둔다. 관리자 서버는 한 대이고, 수험생 서버 DB 역할이 관리자 로그인 잠금을 지우지 못하게 하려는 것이다.

## 응답 스트림 동작

1. 전송: 응답을 맡을 서버가 `ai_streams`에 행을 넣어 예약한다. 이미 살아 있는 행이 있으면 409(답하는 중).
2. 응답 중: 다른 서버가 이 응답의 스냅숏을 요청한 적이 있을 때만, 조각을 모아 짧은 간격으로 대화 전용 채널에 NOTIFY한다. 알림에는 조각의 시작 위치(offset)를 붙인다. 요청 전까지의 텍스트는 스냅숏에 들어가므로 알릴 필요가 없다.
3. 다른 서버에 SSE가 붙으면: 그 서버가 대화 채널을 먼저 LISTEN하고, 스냅숏 요청 채널로 요청한다. 맡은 서버가 지금까지의 텍스트를 행에 쓰고 알린다. 받는 쪽은 스냅숏 뒤에 오는 조각을 offset으로 이어 붙인다. LISTEN이 요청보다 먼저이므로 빠지는 조각이 없다.
4. 끝: 맡은 서버가 done·failed 이벤트를 행에 쓰고 알린다. 받는 쪽은 행에서 이벤트를 읽어 보낸다.
5. 서버가 죽으면: 서버마다 자기 행의 생존 시각을 주기적으로 갱신한다. 일정 시간 갱신이 없는 행은 버려진 것으로 보고 새 전송이 가져간다. 그 응답은 사라지므로 해당 전송은 운영자가 환불한다(단일 서버 재시작 때와 같다).

## 권한

| 테이블 | 수험생 서버 | 관리자 서버 | 채점 워커 |
|---|---|---|---|
| ai_streams | 읽기·추가·수정·삭제(조정용 임시 상태, 기록 아님) | 없음 | 없음 |
| rate_limit_hits | 읽기·추가·삭제 | 없음 | 없음 |

NOTIFY는 PostgreSQL 권한으로 막을 수 없어서 다른 역할도 대화 채널에 알림을 보낼 수는 있다. 받는 쪽은 알림 내용을 화면 표시용 조각으로만 쓰고, 저장되는 응답은 항상 DB의 메시지 행이다. 끝 이벤트는 알림이 아니라 행에서 읽는다.

## 검증 (2026-09-27)

| 항목 | 결과 |
|---|---|
| 통합 테스트 `tests/integration/multi-instance.test.ts` | 6개 통과. A가 맡은 응답을 B의 SSE가 스냅숏·조각·끝까지 받고 받은 텍스트가 저장된 응답과 같다. 끝난 뒤 붙으면 idle. 두 서버 동시 전송은 하나만 받고 토큰도 한 번만 차감. 죽은 서버의 예약은 다른 서버가 가져간다. AI 요청 한도와 로그인 잠금은 두 서버를 합쳐 센다 |
| 권한 테스트 | 두 조정 테이블은 수험생 서버만 다룬다 |
| 부하 테스트(120명, 2대, 라운드로빈) | 오류 0건. 다른 서버에 붙은 스트림 0.5%는 스냅숏 3초 초과로 idle, 화면은 다시 읽고 다시 붙는다. 한 PC에서는 2대가 1대보다 느리다(코어 공유) |

## 코드 리뷰 (2026-09-27)

| 등급 | 지적 | 조치 |
|---|---|---|
| 높음 | 멈춘 것처럼 보였다 살아난 옛 담당 서버가 예약을 빼앗긴 뒤에도 같은 대화 채널로 조각·끝 알림을 보내, 새 담당 서버의 구독자가 중간에 끊길 수 있다 | 모든 알림에 보낸 서버 식별자를 넣고, 구독자는 구독을 시작할 때 행에 적힌 담당 서버의 알림만 받는다. 옛 담당 서버는 생존 표시·스냅숏·끝 기록이 아무 행도 바꾸지 못하면 손을 떼고 자기 구독자에게 idle을 보낸다. 통합 테스트 추가 |
| 중간 | 끝내는 중에 들어온 스냅숏 요청이 끝난 행에 스냅숏을 다시 쓸 수 있다 | 끝내는 중에는 스냅숏 요청을 받지 않는다. 스냅숏은 끝나지 않은 행에만 쓴다 |
| 낮음 | 로그인 실패 기록과 세기를 따로 해 두 서버가 동시에 실패를 기록하면 잠금 기준을 조금 넘길 수 있다 | DB 함수 `rate_limit_record_and_count` 한 번으로 한다(마이그레이션 0006) |

## 조정 시간값 (`server/src/candidate-services.ts`의 `STREAM_HUB_TIMING`)

| 값 | 설정 | 뜻 |
|---|---|---|
| heartbeatMs | 5초 | 맡은 응답의 생존 표시 간격 |
| staleMs | 20초 | 이만큼 표시가 없으면 죽은 서버로 본다 |
| notifyIntervalMs | 50ms | 조각 알림을 모아 보내는 간격 |
| snapshotTimeoutMs | 3초 | 스냅숏 요청을 기다리는 시간 |
| finishedRetentionMs | 1분 | 끝난 응답 행을 남겨 두는 시간 |
