# 부하 테스트: 권한 분리·다중 인스턴스 이후

> 작성: 2026-09-27 · 작성: Claude (Opus 5.5 세션)
> 환경: 개발 노트북 1대(AMD Ryzen 5 230, 논리 코어 12, Windows 11). 부하 발생기, 서버, 임베디드 PostgreSQL 18.4가 모두 같은 PC에서 돈다. 모의 AI(응답 조각 40ms 간격).
> 명령: `npx tsx tests/load/run-load-test.ts 120 180 <대수> burst` (가상 응시자 120명이 2~5초마다 행동, 180초)
> 원자료: `workspace/load-test/load-test-2026-09-27T02-15-28-616Z.json`(1대), `...T02-19-39-387Z.json`(2대), 비교 기준 `...2026-09-26T18-22-49-501Z.json`(분리 전)
> 120분 리허설 결과는 이 문서 끝 '120분 리허설'에 적는다.

## 요약

- **오류는 0건이다.** 1대, 2대(라운드로빈 프록시, 세션 고정 없음) 모두 모든 요청이 성공했다.
- **정상 구간의 중앙값은 분리 전과 같다.** AI 전송 약 20ms, 답안 저장 약 10ms, 상태 조회 약 10ms.
- **나빠진 것 두 가지가 있다.** 120명이 같은 순간에 로그인하는 시작 구간이 2~3초로 늘었다. 약 1분마다 몇 초씩 멈춰 p99가 1~2초로 올랐다.
- **이 PC에서는 2대가 1대보다 느리다.** 두 서버와 부하 발생기, DB가 코어 6개를 나눠 쓰기 때문이다. 다중 인스턴스의 목적은 여러 PC로 나눠 버티고 한 대가 죽어도 시험을 이어 가는 것인데, 이 PC 한 대로는 그 이득을 잴 수 없다.

## 찾아서 고친 것

| 발견 | 근거 | 조치 |
|---|---|---|
| 테스트가 `localhost`로 접속했는데 서버는 IPv4에만 붙어 있었다. Windows에서 IPv6 연결 거절 뒤 약 2초 재시도하고 IPv4로 넘어간다 | 30명만 돌려도 로그인이 약 3초로 고정 | 테스트 주소를 127.0.0.1로 바꿨다(`tests/support/isolated-stack.ts`, E2E 주소) |
| 한 IP에서 로그인이 몰리면 IP 한도 버킷 하나에 잠금 대기가 줄지어 쌓였다 | 한 버킷 120건 동시 처리 879ms, 버킷을 나누면 44ms | IP 한도는 서버마다 메모리로 센다. IP 한도는 로그인 해시 계산으로부터 그 서버의 CPU를 지키는 값이라 서버별이 맞다. 계정 잠금과 AI 요청 한도는 계속 DB에서 전체로 센다(`login-throttle.ts`) |
| 한도 확인·기록이 서버와 DB를 세 번 오가며 잠금을 잡았다 | 위와 같은 대기 | DB 함수 한 번으로 바꿨다(마이그레이션 0005) |
| 모든 응답 조각을 다른 서버에 알려 연결 풀이 알림에 묶였다 | 2대 구성에서 스냅숏 대기 시간 초과 증가 | 다른 서버가 스냅숏을 요청한 응답만 조각을 알린다. 요청 전까지의 텍스트는 스냅숏에 들어간다 |
| 조정용 임시 행(한도 기록, 응답 예약)의 커밋이 디스크 기록을 기다렸다 | DB 표본에서 WAL 쓰기 대기 | 이 행들만 커밋이 디스크 기록을 기다리지 않게 했다(`ephemeral-write.ts`). 대화·원장·답안은 그대로 기다린다 |
| 서버가 막 떴을 때 DB 연결이 비어 있다 | Windows PostgreSQL은 연결마다 프로세스를 띄운다(연결 1개 약 180ms) | 기동 때 연결 풀을 미리 연다(`warmUpConnections`). 효과는 따로 재지 않았다 |

## 남은 것(원인 미확정)

**약 1분마다 몇 초씩 멈춤.** 멈춘 시각은 PostgreSQL 자동 정리(autovacuum·analyze)가 도는 시각과 정확히 겹친다. 그동안 서버 연결 20개가 모두 평범한 조회를 실행 중이고, 잠금이나 I/O 대기는 보이지 않는다.

| 확인한 가설 | 결과 |
|---|---|
| 역할별 계정의 컬럼 권한 검사가 카탈로그 캐시 무효화에 걸린다 | 아니다. 소유자 계정으로 돌려도 같다 |
| 준비된 쿼리(prepared statement)의 계획이 무효화된다 | 아니다. 준비 쿼리를 꺼도 같다 |
| PostgreSQL 18의 비동기 I/O 작업자가 막힌다 | 아니다. `io_method=sync`로 돌려도 같다 |

분리 전 기준 측정(2026-09-26)에는 이 멈춤이 없었다. 남은 가설은 두 가지다. 하나는 이 PC에서 서버·DB·부하 발생기가 코어를 나눠 쓰다가 자동 정리가 겹치면 CPU가 모자라는 것이다. 다른 하나는 분리 뒤 늘어난 연결 수(수험생·관리자 서버 연결, LISTEN 연결)다. 운영과 같은 별도 DB 서버에서 다시 재야 가려진다. 진단 도구는 남겨 두었다.

| 도구 | 켜는 법 |
|---|---|
| DB 대기 표본(시간축, 자동 정리 표시) | `LOAD_TEST_DB_SAMPLING_MS=100` |
| 수험생 서버 CPU 프로파일 | `LOAD_TEST_CPU_PROFILE=1` |
| 1초 넘는 요청 목록 | 결과 JSON의 `slowSamples`(항상) |

## 운영 판단

- 실제 시험에서 로그인은 몇 분에 걸쳐 흩어지므로 시작 구간 2~3초는 최악의 경우다. 줄이려면 시험장 입장을 조별로 나눈다.
- 수험생 서버는 한 PC면 1대로 운영한다. 2대 이상은 서로 다른 PC(또는 코어가 충분한 서버)에 둘 때만 이득이 있다.
- 운영 DB는 별도 서버에 두고, 리허설에서 자동 정리 시각의 지연을 다시 본다.
