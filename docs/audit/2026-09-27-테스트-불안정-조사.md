# 테스트 불안정(간헐 실패) 조사

> 작성: 2026-09-27 · 작성: Claude (Opus 5.5 세션)
> 대상: `npm run test:coverage`, `npm run test:integration`에서 드물게 파일 하나(테스트 5개)가 통째로 실패하던 현상

## 현상

- 2026-09-27 커버리지 실행 한 번에서 `answers-and-notices.test.ts`의 5개가 실행되지 않고 실패로 집계됐다. 이후 7번은 재현되지 않았다.
- 같은 날 반복 실행(`workspace/flake-hunt/run-1.log`~`run-4.log`) 중 4번째에서 다시 나타났다. 이번에는 로그가 남았다.

## 원인

로그의 오류:

```
Error: [vitest-pool]: Worker forks emitted error.
Caused by: Error: Worker exited unexpectedly with exit code 3221225794 during starting state
```

- 3221225794는 `0xC0000142`(STATUS_DLL_INIT_FAILED)다. Windows가 새 프로세스를 초기화하지 못한 것이다. 테스트 코드나 서버 코드의 오류가 아니다.
- Vitest의 기본 풀(forks)은 테스트 파일마다 자식 프로세스를 새로 띄운다. 그 시각에 다른 명령(타입 검사, 다른 Node 프로세스)이 함께 돌면서 프로세스 생성이 몰렸고, 파일 하나의 워커가 시작하지 못했다.
- 이때 테스트 러너가 끝나지 않고 남아 임베디드 PostgreSQL과 데이터 폴더(`workspace/test-postgres-<pid>`)를 붙잡고 있었다. 2026-09-27 확인 후 종료하고 폴더를 지웠다.
- 같은 조사에서 통합 테스트가 느린 이유도 찾았다. Windows의 PostgreSQL은 연결마다 프로세스를 띄우므로(연결 하나 약 180ms), 권한 분리로 역할별 연결이 넷이 되자 테스트마다 연결을 새로 여는 비용이 커졌다. 여기에 테이블 비우기(TRUNCATE, 약 1.1초)가 더해졌다.

## 조치

| 조치 | 파일 |
|---|---|
| 테스트를 자식 프로세스 대신 워커 스레드에서 돌린다(`pool: 'threads'`). 파일마다 프로세스를 만들지 않으므로 이 실패 경로가 없어진다 | `vitest.config.ts`, `vitest.integration.config.ts`, `vitest.coverage.config.ts` |
| 역할별 연결 풀을 테스트 파일 안에서 재사용하고, 파일이 끝나면 닫는다 | `tests/integration/support/test-server.ts` |
| 테스트 사이 데이터 비우기를 TRUNCATE에서 외래키 역순 DELETE로 바꿨다 | 같은 파일 |

## 남은 주의

- 여러 무거운 명령(E2E, 부하 테스트, 커버리지)을 같은 PC에서 동시에 돌리지 않는다. 스레드 풀로 테스트 러너 쪽 위험은 없앴지만, 임베디드 PostgreSQL 백엔드도 프로세스이므로 극단적인 동시 실행에서는 여전히 영향을 받을 수 있다.
