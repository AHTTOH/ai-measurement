## 0. 먼저 결정해야 하는 것 (PRD에 없는 항목)

PRD는 "무엇을 평가하는가"는 분명하지만 "어떻게 만들 것인가"는 비워 두었다. 아래 항목은 구현 방식이 갈리므로 **Phase 0에서 신영환이 확정**해야 한다. 권장안은 내 의견이고, 결정 칸은 비워 두었다.

| D1 | 기술 스택 (언어·프레임워크·DB·호스팅·큐) | server·web·grading 내부 구조와 P1 착수가 여기에 걸린다 | TypeScript 단일 언어. 서버는 상주형 Node 프로세스(120분 세션과 SSE 스트리밍 때문에 서버리스 제외), 웹은 React, DB는 PostgreSQL(원장 차감 트랜잭션), 작업 큐도 PostgreSQL 기반으로 두어 인프라를 늘리지 않는다. 근거: 시험 패키지·API 스키마를 server·web·grading이 한 정의로 공유한다. 대안은 Python(FastAPI) 서버 + React. PRD 12장 MVP 12개 항목을 구현 단위와 단계로 연결한다.

| MVP 항목 | 구현 단위 | PRD 근거 | 단계 |

| 답안 제출 | 자동저장, 버전 누적, 최종 제출, 조건 변경 노출 | 7, 11 | P3 |

| 관리자 결과 페이지 | 시험·응시자 목록, 상세(대화·원장·답안·근거), 내보내기 | 8, 9, 11 | P5 |

PRD에 있지만 MVP 목록에 없는 것과 처리 방침:

- **외부 AI 사용 금지(2장)**: 기술 차단(락다운 브라우저)은 MVP 밖. 감독 + 서약 + 탭 이탈 이벤트 로그(가능하면)로 대체. 로그는 참고용이며 채점에 쓰지 않는다.
- **복붙 방지 설계(5장)**: 플랫폼이 복사를 막지 않는다. 토큰 예산이 억제 장치이고, 자료 안의 함정(불필요 정보·개인정보·인젝션 문자열)은 시험 패키지의 정답 메타로 관리한다.
- **진행 중 조건 변경(7장)**: D7 결정에 따름. 포함 시 P3.

## 2. 시스템 구성 (스택 중립)

```
[응시자 브라우저]        [관리자 브라우저]
       │                        │
       ▼                        ▼
┌──────────────────────────────────────────┐
│ API 서버                                 │
│  · 인증·세션·타이머                       │
│  · 시험 패키지 로드·자료 제공              │
│  · AI 프록시 (Claude 호출은 여기서만)      │
│  · 토큰 원장 (사전 계산 → 원자적 차감)     │
│  · 답안 저장·버전·제출                    │
│  · 감사 로그 (요청·응답 전문)              │
└───────┬──────────────┬───────────────────┘
        │              │
   [관계형 DB]    [파일 저장소]        [Claude API]
   세션·메시지·    시험 자료·첨부·      messages
   원장·답안·채점   제출물             count_tokens
        ▲                              batches
        │
┌───────┴───────────────┐
│ 채점 워커 (비동기)      │
│  · 규칙 채점            │
│  · LLM 채점 (Batches)   │
│  · 집계·플래그          │
└────────────────────────┘
```

구성 원칙:

- **Claude 호출은 서버만 한다.** API 키는 서버 환경변수. 브라우저는 서버의 스트리밍 엔드포인트만 본다.
- **AI 프록시, 토큰 원장, 채점은 서로 독립 모듈**이다. 원장은 AI 프록시를 몰라도 되고, 채점은 서버 없이 DB만 있으면 돈다(재채점 스크립트용).
- **시험 정의는 데이터**다. 배점·토큰 예산·시간·모델·effort·문항 유형은 시험 패키지와 설정 파일에서 온다. 코드에 상수로 두지 않는다.
- **로그는 append-only.** 메시지·원장·답안 버전은 수정·삭제하지 않는다. "어떻게 도달했는가"(PRD 11장)가 평가 대상이기 때문이다.

## 4. 핵심 메커니즘 설계

### 4.1 토큰 원장 (PRD 6장)

흐름:

1. 응시자가 메시지(본문 + 첨부 선택)를 보낸다.
2. 서버가 **전송 전** 토큰 계산 API(`count_tokens`)로 신규 전송분을 센다. 모델은 실제 호출 모델과 동일. 첨부는 서버가 재구성한 실제 전송 형태(CSV 텍스트 블록, PDF base64 document 블록)로 센다.
3. 잔여 < 계산값이면 **거부**하고 사유·계산값·잔여를 화면에 보여준다. 부분 전송이나 자동 축약은 하지 않는다.
4. 잔여 ≥ 계산값이면 트랜잭션 안에서 원장에 차감 행을 추가하고(행 잠금 또는 조건부 갱신으로 동시 전송 방지), 그 다음 Claude를 호출한다.
5. 호출이 실패해도(429·5xx·refusal) 차감은 **취소하지 않는다**가 기본이다. 단, 서버 원인(레이트 리밋·장애)일 때는 운영자가 되돌릴 수 있게 `reason`을 남긴다. 이 정책도 D12와 함께 확정한다.
6. 응답의 `usage`는 Message에 별도 저장한다. 원장 차감량과 다르게 나오는 것이 정상이다(대화 이력 재전송, 캐시).

주의:

- 토큰 계산 API는 추정치이고 실제와 소폭 다를 수 있다(공식 문서). 원장은 계산값 기준으로 일관되게 차감하므로 응시자 간 공정성은 유지된다.
- 계산 API 실패 시 **추정치로 대체하지 않는다.** 전송을 막고 오류를 드러낸다. 폴백 금지 원칙.
- 이중 전송 방지: 클라이언트가 메시지마다 idempotency key를 보내고 서버가 같은 키를 거부한다.
- 잔여 표시는 원장 마지막 행의 balance_after를 그대로 보낸다. 클라이언트가 계산하지 않는다.

### 4.2 AI 프록시 (Claude 연동)

- 모델: `claude-sonnet-5` (PRD 2장 "Claude Sonnet 5"). 시험 설정값.
- 호출 방식: 스트리밍. 서버가 SSE로 응시자에게 중계하면서 동시에 전문을 모아 DB에 저장한다. 응시자가 새로고침해도 서버 측 스트림은 끝까지 진행되고, 재접속 시 저장본을 복원한다.
- thinking: Sonnet 5는 adaptive가 기본이며 `budget_tokens`는 400 오류. `output_config.effort`를 시험 설정값으로 고정(D16). 시험 중 바꾸면 캐시가 깨진다.
- max_tokens: 시험 설정값(권장 8,000). `stop_reason: max_tokens`면 응시자에게 "응답이 길이 제한으로 끊김"을 표시한다.
- tools: 없음(D9). 서버 도구를 붙이면 토큰 계산 API가 거부하고 캐시도 흔들린다.
- 시스템 프롬프트: 시험 전체에 **바이트 단위로 동일**한 고정 문자열. 날짜·응시번호·케이스명을 넣지 않는다(캐시 무효화 방지). Case별 자료는 시스템에 넣지 않는다. 응시자가 무엇을 줄지 판단하는 것이 평가 대상이다(PRD 3장 ①).
- 조건 변경 공지(7장)는 응시자 화면에만 띄운다. AI 대화에 자동 주입하지 않는다. 응시자가 AI에게 알릴지 판단해야 한다.
- 캐싱: 시스템 프롬프트 블록에 명시 breakpoint 1개 + 요청 최상위 자동 캐싱(대화 꼬리). Sonnet 5 최소 캐시 길이 1,024 토큰이므로 시스템 프롬프트가 그보다 짧으면 시스템은 캐시되지 않고 대화 이력만 캐시된다. TTL은 응시자 턴 간격 실측 후 결정(5분 안에 다음 턴이 오면 5분, 아니면 1시간). `usage.cache_read_input_tokens`를 대시보드에 노출해 캐시가 실제로 먹는지 상시 확인.
- 오류 처리: 429는 `retry-after`만큼 대기 후 재시도(큐), 5xx는 SDK 재시도, `refusal`은 그대로 기록하고 응시자에게 표시. 오류를 삼키지 않는다.
- 첨부 전달 형식: CSV는 선택 컬럼·행으로 재구성한 텍스트 블록(구분자·헤더 유지), PDF는 base64 document 블록. 전달된 실제 바이트를 Attachment에 그대로 보관한다.

### 4.3 첨부 데이터 전달과 기록 (PRD 10장 ① 규칙 채점의 근거)

- 응시자 화면에서 자료를 첨부할 때 CSV는 컬럼 체크박스 + 행 필터(선택), PDF는 전체 또는 페이지 범위.
- 서버는 선택 결과로 전송 본문을 만들고 `Attachment`에 material_id, 선택 컬럼, 행 수(또는 행 ID), 렌더링 토큰 수를 기록한다.
- 붙여넣기 본문에도 개인정보 패턴(주민등록번호·전화번호·이메일·카드번호 등)과 시험 패키지의 금지 문자열 사전을 대조해 `pii_hits`를 남긴다. 이건 **기록만** 하고 전송을 막지 않는다. 막으면 평가가 안 된다.

### 4.4 타이머와 세션

- 시작 시 서버가 `expires_at = started_at + duration`을 저장한다. 클라이언트는 서버 시각을 받아 표시만 한다.
- 만료 후 요청은 전부 거부한다(AI 호출·답안 저장). 만료 시 마지막 저장 답안을 자동으로 최종 제출 처리한다.
- 운영자 연장은 AuditEvent로 남긴다(D12).
- 동일 응시번호 중복 로그인 시 이전 세션 토큰을 무효화하고 이벤트를 남긴다.

### 4.5 답안 저장·버전

- 편집 중 일정 간격(예: 3초 디바운스)으로 저장. 저장마다 새 버전 행. 갱신이 아니라 삽입.
- "최종 제출"은 해당 문항의 현재 버전에 is_final을 표시한 새 행을 추가한다.
- 문항 진입·이탈 시 TimeLog를 남긴다.

### 4.6 조건 변경 노출 (PRD 7장)

- SubQuestion.reveal_condition 예: `{after_subquestion_submitted: "1-3"}`, `{after_minutes: 40}`.
- 조건 충족 시 화면에 공지 카드가 뜨고, AuditEvent에 노출 시각을 남긴다. 채점 시 "노출 이후 답안·대화가 바뀌었는가"를 이 시각 기준으로 본다.

### 4.7 보안

- 응시번호 + PIN, 세션 토큰은 httpOnly 쿠키, 시험 시간 창 밖 접근 차단.
- 자료 다운로드는 세션 소유자에게만. 파일명·경로는 서버가 정한다(경로 조작 방지).
- 세션별 요청 레이트 리밋(예: AI 호출 분당 N회)으로 스크립트 남용을 막는다.
- CSP, HTTPS 전용, 기본 보안 헤더.
- API 키·DB 접속 정보는 환경변수. 저장소에 절대 넣지 않는다.
- 시험 자료의 개인정보는 **전부 가공 데이터**로 만든다. 실존 인물 데이터가 Claude API로 나가는 일이 없어야 한다.

## 5. 자동채점 파이프라인 (PRD 8·9·10장)

트리거: 세션 종료(제출 또는 만료) 이벤트 → 채점 큐. 시험 종료 후 일괄 실행이 기본(D10).

### ① 정보 판단 (규칙 기반 우선)

입력: Attachment, Message 본문의 pii_hits, 답안(자료 검토 문항), 시험 패키지의 sensitivity_meta.

규칙 예(시험 패키지 루브릭에 데이터로 정의):

- 필요 컬럼 전달 → 가점, 불필요 컬럼 전달 → 감점
- 개인정보 태그 컬럼·행 전달 → 감점 + Violation(pii)
- 인젝션 태그 행 전달 → 감점 + Violation(injection_forwarded)
- 기밀 태그 자료 전달 → 감점 + Violation(secret)
- 자료 검토 문항(1-1) 답안이 선택형이면 정답 키와 정확 비교, 서술형이면 ② 채점기로 넘긴다

산출: axis=judgment 점수 + evidence(어떤 메시지·첨부가 근거인지 ID 목록).

### ② AI 활용·검증 (LLM 채점)

입력: Case 대화 전문, 답안 버전 이력, 조건 변경 노출 시각, 루브릭.

- 채점 모델에 구조화 출력(`output_config.format`, 스키마 강제)으로 항목별 점수·근거(메시지 ID 인용)·판단 이유를 받는다. 자유 서술만 받지 않는다.
- 루브릭 항목은 PRD 3장 ②의 요소를 그대로 쓴다: 맥락 제공, 요청 적절성, 반복 수정, 계산·사실 검증, 과도한 해석 발견, 그대로 받아들이지 않음, 변경조건 반영.
- "변경조건 반영"은 규칙(노출 이후 답안 버전 변경 여부)과 LLM 판단을 함께 저장한다.
- 프롬프트 형식은 평가하지 않는다(PRD 3장). 루브릭에 형식 항목을 두지 않는다.

### ③ 업무 결과물 (기준답안 + 루브릭)

입력: 최종 답안, 기준답안, 루브릭.

- 수치는 규칙: 기준값과 허용오차를 시험 패키지에 정의하고 답안에서 추출해 비교한다.
- 근거·논리·필수 내용·결론은 LLM 채점(구조화 출력).

### 집계

- Case별 3축 점수 → 시험 총점(배점은 시험 패키지에서). PRD 8장 형태로 관리자 화면에 표시.
- Violation은 점수와 별도로 플래그. 합격 처리는 Exam.violation_policy(D13)에 따른다.
- 채점 결과는 rubric_version, grader, 모델 ID, 요청 ID와 함께 저장한다. 재채점하면 새 행이 추가되고 이전 결과는 남는다.

### 신뢰성 확보

- 골든 세트: 샘플 응시 기록 5~10건을 사람이 채점해 두고, 자동채점과 축별 편차를 측정한다. 편차가 크면 루브릭·프롬프트를 고치고 버전을 올린다.
- 같은 입력을 2회 채점해 편차를 기록한다(effort 고정).
- 구조화 출력 파싱 실패 시 **미채점 상태로 드러낸다.** 0점이나 평균값으로 메우지 않는다.

## 7. 디렉토리 구조 (2026-09-27 승인·생성)

2026-09-27 신영환 승인으로 아래 최상위 폴더를 만들고 각 폴더에 용도·규칙 README를 두었다. **이후 구조의 원본은 루트 `README.md`와 각 폴더 README다.** 이 절은 승인 당시 제안 기록이며, 승인 후 한 곳만 고쳤다. `shared/` 설명에 있던 "배점 기본값"을 뺐다. 기본값은 폴백 금지 원칙과 충돌하므로 배점은 시험 패키지에서만 읽는다. `server/`·`web/`·`grading/` 내부 구조는 D1(스택) 확정 후 다시 제안한다.

```
ai-measurement/

│   ├── audit/            # 점검·부하·채점 검증 리포트 (.md와 .html 나란히)
│   └── runbook/          # 시험 당일 운영 절차
├── exams/                # 시험 패키지. <exam-slug>/exam.json + materials/ + rubrics/ + answer-keys/
│                         # 실제 시험은 gitignore. 샘플 시험 1개만 커밋
├── server/               # API 서버: 인증·세션·타이머·AI 프록시·토큰 원장·답안·감사 로그
├── web/                  # 프론트: candidate/ (응시자) · admin/ (관리자)
├── grading/              # 채점: rules/ · llm/ · aggregate/. 서버 없이 DB만으로 실행 가능
├── shared/               # 공통 스키마·타입·설정 항목 형식 (시험 패키지 스키마 등). 값은 두지 않는다
├── infra/                # DB 스키마·마이그레이션·배포 설정·.env.example

├── tests/                # 단위·통합·e2e·부하
└── workspace/            # 임시 산출물 (gitignored)
```

원칙:

- 파일 이름만 보고 정체를 알 수 있게 짓는다. `data.json`, `utils.ts` 같은 이름 금지.
- 임시 파일은 `workspace/` 아래에만.
- 시험 패키지는 데이터이고 코드가 아니다. `exams/`가 진실의 원천이며 서버는 이를 읽기만 한다.

## 9. 용량·비용·레이트 리밋 계산 (2026-09-27 공식 문서 기준)

### Claude Sonnet 5 레이트 리밋 (Messages API, 티어별)

| 티어 | RPM | 입력 토큰/분 (ITPM) | 출력 토큰/분 (OTPM) | 월 지출 상한 |
|---|---:|---:|---:|---:|
| Start | 1,000 | 2,000,000 | 400,000 | $500 |
| Build | 5,000 | 5,000,000 | 1,000,000 | $1,000 |
| Scale | 10,000 | 10,000,000 | 2,000,000 | $200,000 |

- **캐시 읽기 토큰은 ITPM에 포함되지 않는다.** `input_tokens` + `cache_creation_input_tokens`만 센다. 캐싱이 곧 처리량이다.
- 토큰 계산 API는 무료이고 별도 한도(Start 5,000 RPM)라 Messages 한도를 잠식하지 않는다.
- 신규 조직은 Evaluation 티어로 시작해 위 표보다 낮을 수 있다. D15에서 실측.
- 급격한 사용량 증가에는 별도의 acceleration limit이 걸릴 수 있다. 시험 시작 직후 120명이 동시에 첫 메시지를 보내는 순간이 위험 구간. 서버 큐로 완만하게 흘려보낸다.

### 120명 동시 부하 추정 (가정 명시)

가정: 피크에 응시자당 분당 1회 전송, 대화 컨텍스트 평균 20,000 토큰, 신규 입력 평균 1,000, 응답 평균 1,500.

| 항목 | 캐시 없음 | 캐시 적용 |
|---|---:|---:|
| RPM | 120 | 120 |
| ITPM | 120 × 20,000 = 2,400,000 (**Start 초과**) | 120 × (1,000 신규 + 약 2,500 캐시 쓰기) ≈ 420,000 |
| OTPM | 120 × 1,500 = 180,000 | 180,000 |

결론: 캐싱 없이는 Start 티어에서 시험이 멈춘다. 캐싱이 되면 Start 티어로도 여유가 있다. Build 티어면 캐시가 일부 빠져도 버틴다.

### 비용 추정 (응시자 1명, 가정 명시)

가정: 시험 전체 40턴, 신규 입력 평균 1,000, 컨텍스트 평균 15,000, 응답 평균 1,200. Sonnet 5 단가 입력 $2/M, 출력 $10/M, 캐시 읽기 $0.20/M, 캐시 쓰기(5분) $2.50/M.

| 항목 | 토큰 | 비용 |
|---|---:|---:|
| 신규 입력 | 40 × 1,000 = 40,000 | $0.08 |
| 캐시 쓰기 | 40 × 2,200 = 88,000 | $0.22 |
| 캐시 읽기 | 40 × 15,000 = 600,000 | $0.12 |
| 출력 | 40 × 1,200 = 48,000 | $0.48 |
| **합계 (캐시 정상)** | | **약 $0.90** |
| 캐시 전부 실패 시 | 600,000 × $2/M 추가 | 약 $2.10 |

120명 기준 시험 1회: 약 $110 (캐시 정상) ~ $250 (캐시 실패). 채점은 응시자당 Case 3개 × 약 45,000 입력 + 3,000 출력 ≈ $0.36, Batches 적용 시 절반. 120명 채점 약 $22~$45.

Start 티어 월 상한 $500 안에 시험 2~3회가 들어간다. 그 이상이면 티어 상향 필요.

## 11. 테스트 전략

- **단위**: 토큰 원장(동시 차감, 잔여 부족 거부, idempotency), 규칙 채점(태그별 점수·플래그), 시험 패키지 검증, 노출 조건 평가.
- **통합**: AI 프록시(mock Claude로 스트리밍·오류 경로, 실 API 소량으로 캐시 hit 단언), 채점 파이프라인(고정 입력 → 결정적 규칙 결과).
- **e2e**: 로그인 → Case 1 응시 → 첨부 → 제출 → 만료 → 관리자 조회. 핵심 흐름 1개는 반드시 자동화.
- **부하**: 120 가상 응시자, mock Claude로 서버·DB 병목 확인 후, 실 API 소량(10~20명 규모)으로 레이트 리밋 헤더(`anthropic-ratelimit-*`) 관찰.
- **채점 검증**: 골든 세트 대조 리포트를 `docs/audit/`에 남긴다.
- 커버리지 목표 80%는 `server/`·`grading/`·`shared/`에 적용한다.

## 12. 작업 원칙 적용

- **폴백 금지**: 토큰 계산 실패·채점 파싱 실패·잔여 미확인은 전부 드러낸다. 기본값으로 메우지 않는다.
- **하드코딩 배제**: 모델 ID, effort, max_tokens, 토큰 예산, 시험 시간, 배점, 개인정보 패턴, 금지 문자열 사전의 값은 전부 시험 패키지 또는 환경 설정에 둔다. `shared/`에는 그 형식(스키마)만 둔다.
- **모듈 독립**: 원장·프록시·채점·자료 제공은 서로 import하지 않고 DB 스키마와 공통 타입만 공유한다. 채점은 서버 없이 실행 가능해야 한다.
- **문서화·타임스탬프**: 결정은 `docs/decisions/`, 점검은 `docs/audit/`, 절대 날짜만 쓴다.
- **구조 변경은 승인 후**: 7장 구조와 D14 이동은 2026-09-27 승인 후 적용했다. 이후 최상위 구조 변경도 승인을 받고 `docs/decisions/`에 기록한다.

## 13. Claude API 확인 사실 (2026-09-27)

출처: claude-api 스킬 캐시(2026-06-24 기준) + platform.claude.com 문서 실시간 조회(2026-09-27).

- 모델 ID `claude-sonnet-5`. 컨텍스트 1M, 최대 출력 128K(대용량은 스트리밍 필수). 단가 입력 $2/M, 출력 $10/M.
- thinking: adaptive가 기본이며 `budget_tokens`는 400 오류. effort는 `low`·`medium`·`high`·`xhigh`·`max`.
- assistant prefill은 400 오류. 응답 형식 제어는 `output_config.format`(구조화 출력)으로.
- 프롬프트 캐싱: 최소 캐시 길이 Sonnet 5는 1,024 토큰. 최대 breakpoint 4개. 5분 TTL 쓰기 1.25배, 1시간 TTL 쓰기 2배, 읽기 0.1배. 요청 최상위 `cache_control`로 자동 배치 가능.
- Sonnet 5는 mid-conversation system message(`role: "system"` in messages) 미지원.
- 토큰 계산 API: 무료, Messages와 독립된 한도(Start 5,000 / Build 10,000 / Scale 20,000 RPM). 추정치이며 실제와 소폭 다를 수 있음. 시스템 프롬프트·클라이언트 도구·이미지·PDF(base64) 지원. 서버 도구와 url·file 소스 문서는 오류.
- 레이트 리밋: 9장 표. 캐시 읽기 토큰은 ITPM 미포함. 응답 헤더 `anthropic-ratelimit-*`로 잔여 확인 가능.
- Message Batches: 비동기, 50% 비용, 결과는 `custom_id`로 매칭.
- 구조화 출력: `output_config.format` + 스키마. citations와 동시 사용 불가.
